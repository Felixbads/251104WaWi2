A. BLOCKER (P0) — SOFORT UMSETZEN

A1) Datenbank & Schema (Migrationen)
	1.	Tabelle Watermarks
	•	vendon_watermarks(machine_id TEXT PRIMARY KEY, last_updated_at TIMESTAMP NOT NULL)
	2.	Idempotenz & Delta
	•	Unique-Index: transactions(machine_id, vendon_id)
	•	Index: transactions(updated_at)
	3.	ORM/Schema anpassen (z. B. shared/schema.ts) – die obigen Constraints/Indizes müssen dort widerspiegeln.
	4.	Anwenden: Lokale Migrationen ausführen; Nachweis über Schema-Dump/ORM-Status.

A2) API-Client (z. B. server/services/vendonSync.ts)
	1.	Parameter erzwingen:
	•	machine_id immer setzen, sonst throw.
	•	search_time='updated' standardmäßig im Delta-/Scheduler-Pfad.
	•	sort='-transaction_id' als Default.
	2.	Auth sichern:
	•	Hardcoded/Fallback API-Key entfernen. Nur ENV akzeptieren, sonst fail-fast mit klarer Fehlermeldung.
	3.	Rate-Limit beachten:
	•	Bei HTTP 429: Retry-After aus Header parsen, pausieren, danach retry.
	•	Backoff-Strategie beibehalten/ergänzen (aber Retry-After priorisieren).

A3) Persistenz/Storage (Upsert statt Duplikat-Hacks)
	1.	Upsert-Funktionen einführen:
	•	upsertTransaction(tx) & upsertTransactionsBatch(list)
	•	Konfliktschlüssel: (machine_id, vendon_id); DO UPDATE mit Feldern (inkl. updated_at).
	2.	Alte Duplikatlogik entfernen:
	•	Kein Modifizieren/“Umbenennen” von IDs mehr.
	•	Kein manueller Vorab-Existenzcheck als Hauptpfad – Upsert erledigt das.

A4) WatermarkStore (neu)
	1.	Implementierung:
	•	get(machineId) -> Date | null
	•	set(machineId, ts: Date)
	2.	Fortschreibung:
	•	Nach jedem Batch: Watermark auf max(updated_at) der eingeflossenen Transaktionen setzen (nur bei erfolgreichen Writes).

A5) Backfill-Service & CLI
	1.	Service HistoricalBackfillService.runBackfill(machineId, fromTs, toTs, chunkDays=14, pageSize=500, dryRun=false, maxPagesPerWindow?)
	•	Chunking (Fenster), Pagination (limit/offset), Safety-Valve (maxPagesPerWindow)
	•	dryRun=true → keine DB-Writes (hart sicherstellen)
	2.	CLI npm run backfill -- --machine-id=<id|all> --from=<UNIX> --to=<UNIX> --chunk=<tage> --limit=<n> --dry-run --concurrency=<n> --max-pages-per-window=<n>
	•	Exit-Codes: 0=OK, >0=Fehler

A6) Scheduler auf Delta-Sync umstellen
	1.	Pro Maschine Watermark laden → Zeitfenster ableiten.
	2.	Delta-Request: search_time=updated + sort=-transaction_id + Pflicht machine_id.
	3.	Nach erfolgreichem Lauf Watermark aktualisieren.
	4.	Parallel-Läufe verhindern (Lock je machine_id oder zentrale Orchestrierung).

D. AKZEPTANZKRITERIEN (Go/No-Go – alle erfüllt, sonst „Nicht fertig“)

	2.	API-Client korrekt: machine_id erzwungen, search_time=updated in Delta-Pfad, Default sort=-transaction_id, kein Hard-Key, 429/Retry-After aktiv.

	5.	Backfill CLI: läuft; Dry-Run schreibt nichts; Live upsertet ohne Duplikate; Exit-Codes korrekt.
	6.	Scheduler: arbeitet im Delta-Modus (Watermark-basiert) und nutzt die erzwungenen API-Parameter.
	7.	Observability: Logs/Metriken vorhanden und sinnvoll.
