1) Kurzdiagnose
• Der resiliente Vendon-Hintergrunddienst wird nie aktiviert, weil `autoStartResilientSync` nirgends importiert wird und deshalb die in `process.nextTick` hinterlegte Initialisierung ausbleibt. 【F:server/services/autoStartResilientSync.ts†L1-L37】【d0e80a†L1-L4】
• Mehrere Scheduler-Implementierungen laufen parallel (z. B. `vendonScheduler.start()` beim Import), wodurch mehrere gleichzeitige Abfragen gegen Transaktionen, Events und Refills ausgelöst werden. 【F:server/services/vendonScheduler.ts†L1-L157】【F:server/routes/sync.ts†L1-L220】
• Die zentralen Vendon-Sync-Routinen verwenden keine Locks für Transaktionen/Events/Refills, so dass gleichzeitige Aufrufe konkurrieren und zu Duplikaten oder inkonsistenten Ergebnissen führen können. Nur der Produkt-Sync nutzt derzeit `acquireSyncLock`. 【F:server/services/vendonSync.ts†L1063-L1406】【F:server/services/vendonSync.ts†L2143-L2200】
• Betroffene Komponenten: `server/services/autoStartResilientSync.ts`, `server/services/vendonBackgroundService.ts`, `server/services/vendonScheduler.ts`, `server/services/vendonSync.ts`, `server/routes/sync.ts`.

2) Minimal reproduzierbare Schritte (in Replit)
1. Replit-Projekt öffnen → Shell starten.
2. `npm install` ausführen, anschließend `npm run dev` starten.
3. In der Konsole beobachten, dass Logs aus `Vendon Scheduler` erscheinen, aber kein "Resiliente Vendon-Synchronisation"-Start-Log (Hintergrunddienst bleibt aus). Parallel dazu `curl -X POST http://localhost:$PORT/api/sync/vendon/transactions -H "Content-Type: application/json" -d '{}'` ausführen und doppelte/überlappende Sync-Logs im Terminal sehen.

3) Fix-Plan (Schritt-für-Schritt)
1. `server/index.ts`: Einmalige Initialisierung von `autoStartResilientSync` importieren, damit der neue Hintergrunddienst automatisch startet. — Warum: sorgt für den vorgesehenen resilienten Dauerlauf statt manuellem Start.
2. `server/services/vendonScheduler.ts`: Auto-Start entfernen oder hinter Feature-Flag (`ENABLE_LEGACY_VENDON_SCHEDULER`) legen, damit nicht mehrere Scheduler parallel laufen. — Warum: verhindert konkurrierende Legacy-Syncs.
3. `server/services/vendonSync.ts`: Für `syncTransactions`, `syncEvents`, `syncRefills` Lock-Handling mit `acquireSyncLock`/`releaseSyncLock` implementieren (inkl. `try/finally`). — Warum: blockiert parallele API-Läufe und vermeidet inkonsistente Ergebnisse.
4. `server/routes/sync.ts`: HTTP-Endpunkte so anpassen, dass sie bei aktivem Lock einen 409-Status oder Hinweis zurückgeben und optional den Hintergrunddienst triggern statt direkten Mehrfachaufruf. — Warum: Benutzer bekommen klares Feedback statt silent competition.
5. `docs/README` o. ä.: Kurze Betriebsanweisung ergänzen (wann Scheduler aktiv ist, wie Locks funktionieren). — Warum: Betriebsteams wissen, welche Tasks laufen.

• `server/services/vendonSync.ts`
```ts
const lockAcquired = await acquireSyncLock(SYNC_TYPE.TRANSACTIONS);
if (!lockAcquired) {
  await storage.updateSyncLog(syncLogId, { syncStatus: 'skipped', errorMessage: 'Transaction sync already running' });
  return { syncLogId, status: 'locked', message: 'Transaction sync already running elsewhere' };
}

try {
  ...
} finally {
  await releaseSyncLock(SYNC_TYPE.TRANSACTIONS);
}
```
Analog für `SYNC_TYPE.EVENTS` und `SYNC_TYPE.REFILLS` mit passenden Meldungen.

```ts

  return res.status(409).json(result);
```

Hinweis: Den Response-Status nur für Lock-Konflikte auf 409 setzen.
