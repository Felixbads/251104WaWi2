Abgleich Lagerbestand vs. Bewegungen (OUT als negativ interpretieren):
SELECT ii.warehouse_id,
       ii.product_id,
       ii.quantity AS current_qty,
       SUM(
         CASE
           WHEN im.movement_type = 'OUT' AND im.source_type = 'warehouse' AND im.source_id = ii.warehouse_id
             THEN -im.quantity
           WHEN im.destination_type = 'warehouse' AND im.destination_id = ii.warehouse_id
             THEN im.quantity
           ELSE 0
         END
       ) AS movement_balance
FROM inventory_items ii
LEFT JOIN inventory_movements im
       ON im.product_id = ii.product_id
      AND (
           (im.source_type = 'warehouse' AND im.source_id = ii.warehouse_id) OR
           (im.destination_type = 'warehouse' AND im.destination_id = ii.warehouse_id)
          )
WHERE ii.warehouse_id = :warehouse_id AND ii.product_id = :product_id
GROUP BY ii.warehouse_id, ii.product_id, ii.quantity;

D) Gaps & Ursachen
Keine Refill-Erfassungsseite/Submit-Logik im Frontend – man kann keine strukturierte Payload senden; Link verweist auf nicht existierende Route.
API verlässt sich auf URL-warehouseId; fehlende Ermittlung der Lagerzuordnung über machine_warehouse_assignments erlaubt falsche Quellen ohne Fehlermeldung.
Lagerabgang validiert Bestand nicht: Math.max(0, …) verhindert Fehlermeldungen bei zu geringer Menge; keine 422/409 für Unterdeckung.
Keine FIFO-/Chargenauswahl: Batch muss extern geliefert werden, sonst batchId leer → keine Priorisierung, Altbestände bleiben liegen.
Bewegungslog nutzt nur movement_type='OUT'/positive quantity; geforderter Negativ-Delta und Typ „FILL“ fehlen, Audit-Auswertung wird erschwert.
Kein Transaktionsrahmen oder Sperren; Lager-, Batch- und Log-Updates laufen getrennt → Risiko inkonsistenter previous_stock/current_stock bei parallelen Refills.
Zeitstempel verlassen sich auf DB-defaultNow() (UTC); keine Umstellung auf Europe/Berlin ersichtlich.
E) Minimaler Nachweis-Plan
Seed: Lege Warehouse, Produktbestand und Charge an (inventory_items, product_batches). Verknüpfe Automaten via machine_warehouse_assignments manuell.
Trigger Refill: POST /api/warehouse3/warehouses/:warehouseId/refills mit { machineId, refillDate, performedBy }, anschließend POST /api/warehouse3/warehouses/:warehouseId/refills/:refillId/items mit { productId, batchId, quantity }. Erwartung: Lagerbestand sinkt exakt um quantity.
Kontrolle: Führe die Queries aus Abschnitt C für das betreffende Produkt/Lager aus, prüfe previous_stock, current_stock und Batch-Bestände. Dokumentiere Abweichungen (z. B. wenn previous_stock < quantity auftritt).
Zeitprüfung: Vergleiche refill_trackings.refill_date, inventory_movements.performed_at mit lokalen Europe/Berlin-Werten; erwarte derzeit UTC-Offsets wegen fehlender TZ-Anpassung.
