Executive Summary
Gesamtgesundheit: 28/100. Kritische Sicherheitslücken (unauthentifizierte SQL-Ausführung, harte Secrets) dominieren die Bewertung.
Funktionsfähigkeit: 40/100. Umfangreiche Features existieren, aber ohne Tests und mit riskanter Demo-Auth bleibt Stabilität fraglich.
Kernprobleme:
/api/execute-sql erlaubt beliebiges SQL ohne Authentifizierung.
Demo-Admin und Auto-Login im Frontend umgehen jede Sicherheitskontrolle.
SMTP- und Vendon-API-Zugangsdaten sind fest eingecheckt bzw. als Default hinterlegt.
Architektur-/Stack-Überblick
Frontend: React 18 mit Wouter-Routing, React Query und Tailwind, gebündelt via Vite; API-Aufrufe standardmäßig gegen /api。
Backend: Express-Server (ESM) mit Drizzle ORM, großer monolithischer server/index.ts, viele Routendateien für Inventar, Lieferanten, E-Mail etc.
Shared: shared/schema.ts enthält Drizzle-Schema für PostgreSQL inklusive zahlreicher Geschäftsobjekte (sync logs, suppliers, orders, etc.).
Integrationen: Vendon REST API (mehrere Sync-Services), OpenWeather OneCall, Cloudinary Uploads, SMTP-Versand.
Ops/Tools: Scripts-Verzeichnis für Datenbereinigung, Drizzle-Kit Migration, Python Prophet-Forecasts.
Funktionsfähigkeit: Buildbarkeit, Tests, kritische Pfade
Build/Run: npm run dev startet Express+Vite, npm run build bundelt Client & Server, npm run start bedient dist. Keine Testskripte vorhanden.
Migrations-/DB-Setup über drizzle-kit push (npm run db:push).
Kritische Pfade (Bestellungen, Inventar, Supplier Portal) existieren, greifen jedoch häufig direkt auf SQL zu und umgehen Geschäftslogik-Schichten.
Tests: keine Unit/Integrationstests; Demo-Login im Frontend macht jede Auth-Prüfung obsolet, daher unklar ob reale Auth überhaupt funktioniert.
Top-Risiken & Belege
R1: Unauthentifizierte SQL-Ausführung erlaubt beliebige Datenmanipulation – /api/execute-sql ist frei zugänglich und führt Query-Strings direkt aus.
R2: Harte Demo-Admin-Creds & Auto-Login – Backend akzeptiert Admin/Admin123, speichert Tokens im Speicher, Frontend erstellt bei jedem Load einen Admin-Token.
R3: Geheimnisse im Repo & Default-API-Key – SMTP-Passwort im Klartext, Vendon-API-Key Hardcoded-Fallback, Cloudinary fallback cloud_name。
R4: Supplier-Portal generiert Sessions via Math.random ohne Ratelimit, ermöglicht Session-Forecasting/Guessing.
R5: Keine Tests/CI + node_modules eingecheckt → Hoher Wartungsaufwand, fehlende Qualitäts-Sicherung.
Handlungsempfehlungen: Quick Wins (2–10 Tage), Epics (4–12 Wochen)
Quick Wins siehe JSON: (1) Direct-SQL abschalten/absichern, (2) Secrets rotieren & aus Repo entfernen.
Zusätzliche kurzfristige Maßnahme: Demo-Login im Frontend abschalten und nur nach erfolgreicher Backend-Auth Token speichern.
Epics: (a) Produktionsreife Auth mit persistentem Userstore, RBAC und Tests. (b) Backend modulieren, Domain-Services extrahieren, CI+Tests etablieren (s. JSON).

Gaps: Keine Tests, keine Lint-Checks, kein CI Gate.
