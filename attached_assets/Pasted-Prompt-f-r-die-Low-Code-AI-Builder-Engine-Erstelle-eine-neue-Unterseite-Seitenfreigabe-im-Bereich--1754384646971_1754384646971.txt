Prompt für die Low-Code/AI-Builder-Engine
Erstelle eine neue Unterseite „Seitenfreigabe“ im Bereich „Einstellungen“.
1. Datenmodell • Lege eine Collection / Tabelle page_permissions an.   • Felder: page_id (Text, Primary Key), page_title (Text), visible_for_employee (Boolean, Default false). • Befülle die Tabelle automatisch mit allen aktuell existierenden App-Seiten (auch ausgeblendete). Füge bei zukünftigen Seiten on-create einen Record hinzu.
2. UI-Aufbau der Seite „Seitenfreigabe“ • Überschrift „Seitenzugriff für Mitarbeitende“. • Eine wiederholte List-Komponente, deren Datenquelle page_permissions ist, sortiert alphabetisch nach page_title. • In jedem List-Item:   – Label = page_title   – Checkbox / Toggle gebunden an visible_for_employee. • Oberhalb der Liste: Suchfeld → filtert live nach page_title. • Unterhalb: „Alles auswählen“ / „Alles abwählen“ Buttons, die visible_for_employee für alle Records setzen.
3. Logik beim Umschalten • Beim Ändern der Checkbox aktualisiere sofort (PATCH) das Feld visible_for_employee des betreffenden Records. • Keine zusätzliche Hard-Codierung in den Seiten selbst: Die Navigation- und Sichtbarkeits-Regeln jeder App-Seite prüfen beim Rendern lediglich zwei Bedingungen   1. current_user.role == 'Mitarbeiter'   2. In page_permissions ist visible_for_employee == true für die eigene page_id • Werden beide erfüllt → Seite anzeigen; andernfalls ausblenden. • Für alle anderen Rollen (z. B. Admin) gilt automatisch volle Sichtbarkeit.
4. Initiale Voreinstellung • Setze bei Erstinstallation für Mitarbeitende nur folgende Seiten auf true: Warenumlagerung, Lagerbestand, Automaten, Produkte, Produzenten, Bestellungen, Wareneingang. • Alle weiteren stehen auf false, können aber jederzeit aktiviert werden.
5. UX-Details • Zeige oben einen Info-Banner: „Änderungen wirken sofort für alle Mitarbeitenden.“ • Nutze Optimistic UI – setze den Haken sofort, rolle zurück, falls das Backend-Update fehlschlägt. • Bei leeren Ergebnissen (Suche) → Placeholder „Keine Seiten gefunden“.
6. Sicherheit • Stelle sicher, dass Mitarbeitende die Seite „Seitenfreigabe“ selbst nicht im Menü sehen (Sichtbarkeit nur für Rolle Admin). • Führe jede Sichtbarkeitsprüfung server-seitig oder über sichere Rules (z. B. Firestore Rules / Supabase RLS), nicht nur client-seitig.
7. Wartbarkeit • Schreibe eine Utility-Funktion registerPage(page_id, page_title), die beim Bauen neuer Seiten automatisch aufgerufen wird und – falls der Eintrag nicht existiert – einen Record in page_permissionsanlegt. • Dokumentiere dieses Pattern für künftige Entwickler*innen.
Ergebnis: Eine wartungsarme „Seitenfreigabe“-Verwaltung, mit der ich (Admin) jederzeit per Checkbox steuern kann, welche App-Bereiche für meine Mitarbeitenden sichtbar sind – ganz ohne nachträgliches Hardcoding in jedem einzelnen Page-Layout.

Umsetzung dieser Aufgaben ermöglicht eine flexible, zentral verwaltbare Steuerung der Seitenfreigaben für Mitarbeitende, inklusive sicherer Serverregeln und eines wartbaren Registrierungsprozesses.
1. Fehlende Datenbankstruktur für Seitenberechtigungen
Ein zentrales Modell zur Verwaltung der Seitenfreigaben existiert nicht. Ohne dieses Modell können weder Sichtbarkeiten gespeichert noch zentral verwaltet werden.
1. **`shared/schema.ts`**: Neue Tabelle `page_permissions` mit Feldern * `page_id` (text, primary key) * `page_title` (text) * `visible_for_employee` (boolean, default `false`) 2. **Migrationsskript**: Drizzle-Migration erstellen/ausführen, um die Tabelle in der Datenbank anzulegen. 3. **Initialbefüllung**: Einmaliges Skript oder Seed-Logik, die alle bestehenden App-Seiten erfasst und als Datensätze einfügt (auch ausgeblendete Seiten). 4. **Defaults**: Für Seiten `Warenumlagerung`, `Lagerbestand`, `Automaten`, `Produkte`, `Produzenten`, `Bestellungen`, `Wareneingang` den Wert `visible_for_employee` auf `true` setzen, alle anderen auf `false`.

2. Kein Backend-Endpunkt zur Pflege von Seitenberechtigungen
Es fehlt eine API, über die die UI die Seite/Checkbox-Änderungen persistieren kann.
1. **`server/routes/page-permissions.ts`** (neu): * `GET /api/page-permissions`: Liste aller Seitenberechtigungen (alphabetisch sortiert). * `PATCH /api/page-permissions/:page_id`: Feld `visible_for_employee` aktualisieren. * `POST /api/page-permissions/register`: `registerPage`-Funktion (siehe Task 3) aufrufen. * Alle Routen nur für `admin` zugänglich machen (Middleware wie `requireAdmin`). 2. **`server/routes.ts`**: Neue Route einbinden. 3. **`server/storage/database-storage.ts`**: Methoden * `getPagePermissions`, `updatePagePermission`, `registerPage`. 4. **Sicherheitsregeln**: Serverseitig prüfen, ob der aufrufende Nutzer `admin` ist.

3. Keine automatische Registrierung neuer Seiten
Neue Seiten müssen manuell in die Tabelle eingetragen werden.

1. **Backend (`server/storage/database-storage.ts`)**: Funktion `registerPage(page_id, page_title)` * Prüft, ob `page_id` existiert; falls nicht, Insert mit `visible_for_employee=false`. 2. **Frontend (`client/src/lib/pagePermissions.ts` oder ähnlicher Pfad)**: * Exportierte Funktion `registerPage(page_id, page_title)` ruft `POST /api/page-permissions/register` auf. 3. **Nutzung**: In jedem neuen Seitenmodul (z.B. direkt in `useEffect` im Page-Component) `registerPage()` aufrufen. 4. **Dokumentation**: Richtlinie in `docs/page_permissions.md` (oder bestehende Dev-Dokumentation) beschreiben, wann und wie `registerPage` aufzurufen ist.
