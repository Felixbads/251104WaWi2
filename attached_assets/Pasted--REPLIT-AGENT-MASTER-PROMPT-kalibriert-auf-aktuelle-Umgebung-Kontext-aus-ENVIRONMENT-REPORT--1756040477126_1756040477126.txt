## Arbeitsprinzipien (nicht verhandelbar)
1. **Keine Geheimnisse leaken**: nur Variablennamen (z. B. `SESSION_SECRET`, `DATABASE_URL`), niemals Werte.
2. **Atomare Schritte**: pro Schritt **genau 1** Thema fixen/ergänzen.
3. **Verbindlicher Prozess je Schritt**: **PLAN → DIFF → SELF‑CHECK → EVIDENZ → ROLLBACK → DOKU**.
4. **Reversibel bleiben**: bei destruktiven/risikobehafteten DB-Schritten zunächst **nur PLAN** liefern.
5. **Qualitätstor**: `npm run check` muss grün sein **vor** Ergebnisabgabe.
6. **Minimal-invasiv**: keine Großumbauten ohne klaren Nutzen und Nachweis.

## Detail‑Definition‑of‑Done (DoD) je Schritt

### 1) Sichere Sessions (express‑session) & Hash‑Audit
- `express-session` in `server/index.ts` einbinden mit:
  - `secret: process.env.SESSION_SECRET`
  - **Store**: `connect-pg-simple` mit bestehendem PG‑Pool (oder generiertem Pool mit `DATABASE_URL`)
  - Cookie: `{ httpOnly: true, secure: NODE_ENV==='production', sameSite: 'lax', maxAge: 8h }`
- **bcrypt‑Audit**: Prüfe Login‑Flow auf `bcrypt.compare(...)` ( vorhandene Nutzung belegen ).
- **Smoke‑Probe**: erfolgreicher Login → Session‑Cookie Flags sichtbar.
- **Docs**: `docs/security.md` Abschnitt „Sessions & Cookies“ + README Env‑Variablen‑Liste (nur Namen).

### 2) helmet + CSP + CSRF
- `helmet()` in `server/index.ts` aktivieren.
- CSP‑Baseline: `script-src 'self'` (+ notwendige CDNs/hosts, falls im Frontend genutzt).
- CSRF‑Schutz:
  - Für stateful Form‑/Cookie‑Flows `csurf` integrieren; für reine API‑Calls saubere, dokumentierte Ausnahme/Double‑Submit‑Cookie.
- **Evidenz**: Response‑Header zeigen Helmet/CSP; geschützter POST ohne Token schlägt fehl.

### 3) Globales Rate‑Limit + Login‑Schutz
- Global: `express-rate-limit` (z. B. 100 Requests / 15 min / IP).
- Login‑Route: strengeres Limit (z. B. 10 / 10 min / IP).
- **Evidenz**: 429 bei Überschreitung (kurzer Log/Antwortauszug).

### 4) Upload‑Härtung
- Aktuelle Upload‑Route ergänzen um:
  - `limits: { fileSize: <z. B. 5*1024*1024> }`
  - strikten MIME‑Filter (Whitelist)
  - **Dateinamen‑Sanitizing** (z. B. `path.basename`, Entfernen unsicherer Zeichen, optional UUID‑Rename)
- **Evidenz**: Großer/unerlaubter Upload wird abgewiesen.

### 5) Drizzle‑Migrations (Baseline) + Indizes (CONCURRENTLY)
- `migrations/` anlegen, Drizzle‑Migrations aktivieren (kompatibel zu vorhandenem `db:push` oder `drizzle-kit`).
- **Erste Migration** nur mit Indizes (ohne Schema‑Breaks):
  - `transactions (location_id, datetime DESC)`
  - `events (machine_id, datetime DESC)`
  - `refills (machine_id, datetime DESC)`
  - `inventory_items (warehouse_id, product_id)` (falls nicht vorhanden)
  - Syntax: `CREATE INDEX CONCURRENTLY IF NOT EXISTS …`
- **Evidenz**: `EXPLAIN` der Hot‑Queries zeigt Index‑Nutzung.

### 6) JSON‑Logs + Request‑IDs + Health (DB+Python)
- Middleware: `X‑Request‑ID` (UUID v4) erzeugen & in JSON‑Logs schreiben (Felder: `ts`, `rid`, `method`, `path`, `status`, `latencyMs`).
- Health‑Route (`/api/inter-app/health`) um **DB‑Ping** + **Python‑Reachability** erweitern (kurzer Testcall auf Child‑Process mit Timeout).
- **Evidenz**: JSON‑Log‑Zeilen + Health‑Antwort `{ ok:true, db:'up', ml:'up' }`.

### 7) Python‑Child‑Process: Timeout/Parallelität + Zod‑Validation
- In `server/services/prophetService.ts`:
  - **Timeout** (z. B. 60 s), **MAX_PARALLEL** (z. B. 2), sauberes Kill‑Handling (SIGKILL).
  - **Zod‑Schema** für Forecast‑JSON (`horizon`, `data: [{ ts, yhat }]`) und Validation vor Nutzung.
- **Evidenz**: Timeout greift bei Hänger; invalider Output wird abgefangen.

### 8) Cron‑Robustheit
- Retry‑Policy mit exponentiellem Backoff, begrenzten Versuchen.
- Idempotenz‑Keys (Duplikat‑Vermeidung).
- Tabelle `job_failures` für Dead‑Letter/Fehler‑Persistenz.
- **Evidenz**: Fehlgeschlagener Run → Eintrag in `job_failures`.

### 9) API‑Versionierung `/api/v1` + OpenAPI‑Stub
- Router‑Prefix `/api/v1`.
- Minimal‑`openapi.yaml` (oder Generierung via `zod-to-openapi` aus existierenden Zod‑Schemas).
- Pagination‑Konvention (limit/cursor) vereinheitlichen & dokumentieren.
- **Evidenz**: `GET /api/v1/...` erreichbar; `openapi.yaml` vorhanden.

### 10) Smoke‑Tests (Server)
- **Jest** Setup unter `server/__tests__/`.
- Tests:
  1. **Login‑Flow** (korrekt/inkorrekt) inkl. Cookie‑Flags
  2. **Orders‑CRUD** (create/read/update/delete)
  3. **Kleiner Vendon‑Sync‑Batch** (Mock/Fixture)
  4. **Forecast‑Endpoint** (Schema‑Validierung)
- **Evidenz**: `npm test` grün (kurzer Zusammenfassungsauszug).
